# Plan Bundle Debugging

Use this guide when a user gives a repository path and asks whether a coflow plan-exec run happened as intended.
The goal is to diagnose the active plan bundle without taking over the workflow or rewriting bundle state.

## Debugging Contract

- Debug from the target repository root, not from the coflow source repository unless the target is coflow itself.
- Treat `co.py flow` stdout as the runtime contract.
- Use `flow_log.ndjson` as a chronological trace, not as canonical state.
- Do not decide gate readiness, next task, completion, halt, or repair by hand.
- Do not edit `plan_seed.yaml`, `tasks.yaml`, `interview.yaml`, `status.yaml`, `notes.yaml`, or `evidence.yaml` while debugging a user run.
- If the finding requires changing the approved plan contract, report the issue instead of repairing the bundle directly.

## Inputs

Required target:

- A repository root path provided by the user or resolved from the current working directory.

Expected bundle layout:

```text
.agents/plan/
  exec.yaml
  {plan-id}/
    plan_seed.yaml
    tasks.yaml
    interview.yaml
    status.yaml
    notes.yaml
    evidence.yaml
    flow_log.ndjson
    evidence/
```

Use the active plan selected by `.agents/plan/exec.yaml`.
If the user names a specific plan id, inspect that plan directory and compare it with the active selection.

## First Pass

Run these from the target repository root.

```bash
pwd
test -f .agents/plan/exec.yaml && sed -n '1,80p' .agents/plan/exec.yaml
~/.codex/skills/coplan/scripts/co.py flow status
```

If the installed CLI path is not available but the target is the coflow repository, use:

```bash
skills/coplan/scripts/co.py flow status
```

Interpret `flow status` as read-only diagnostics only.
It can say which boundary is pending, but it is not the source for the next action.
Use `co.py flow next` only when the user asked to continue or when the debugging task explicitly includes reproducing the next root boundary.

## Canonical State Surfaces

| Surface | Use |
|---|---|
| `co.py flow status` | Read-only snapshot of phase and pending boundary. |
| `co.py flow next` | Runtime contract that emits the next `root_action`. |
| `status.yaml` | Stored phase, current task, task states, halt state. |
| `evidence.yaml` | Recorded verification evidence; loose files under `evidence/` are not enough. |
| `notes.yaml` | Durable decisions, risks, repairs, and halt notes. |
| `flow_log.ndjson` | Append-only event trace for reconstructing how the state happened. |

Do not treat `flow_log.ndjson` as the current state.
Use it after reading the canonical state to explain transitions, missing boundaries, or responsibility leaks.

## Trace Reading

Start with the tail of the log, then widen only as needed.

```bash
tail -n 80 .agents/plan/<plan-id>/flow_log.ndjson
```

High-value event families:

| Event | What It Proves |
|---|---|
| `flow.command.start` | A public `co.py flow` command began. |
| `root_action.emit` | Control returned to the root agent at a real boundary. |
| `flow.command.end` | A public `co.py flow` command ended and records the emitted action. |
| `flow.command.error` | The CLI hit an unrecovered command error. |
| `interview.*` | Planning interview, answer recording, scoring, closure, or follow-up behavior. |
| `codex_agent.*` | Private CLI subagent execution behind the public flow command. |
| `bundle.authored` | `tasks.yaml` was generated by the planner path. |
| `seed_feedback.classified` | User plan-seed feedback was classified before mutation. |
| `state.transition` | A saved YAML field changed. |
| `task.claimed` | CLI selected the current task. |
| `evidence.recorded` | Verification output was recorded through `flow evidence`. |
| `task.completed` | CLI completed a task after required evidence passed. |
| `repair.applied` | CLI applied a contract-compatible repair. |
| `halt.recorded` | CLI recorded a halt boundary. |
| `execution.completed` | CLI completed the entire execution after finish gates passed. |

Useful trace patterns:

- Every `root_action.emit` should be paired with `flow.command.end`; later state changes should be driven by a new public `flow.command.start`, not direct bundle edits.
- A failed `evidence.recorded` should lead back to `root_action.emit` with `repair_task` or continued current-task execution.
- `task.claimed` and `task.completed` should come from CLI events, not manual `status.yaml` edits.
- `codex_agent.*` should appear between CLI command events and should not become a root-facing contract.
- `execution.completed` should appear only after all tasks, including final verification tasks, are `Done`.

## Planner Debugging

Use this when phase is `planning` or `seed_review`, or when execution seems to have started from a weak plan.

Check:

- `.agents/plan/exec.yaml` points at the expected active plan.
- `interview.yaml.initial_context` exists and matches the user's original request.
- `interview.yaml.pending_user_question` matches an `ask_user` boundary when present.
- `interview.yaml.status` is `closed` only after enough answered rounds, fresh ambiguity scoring, closure audit, and no material blockers.
- `plan_seed.yaml` exists only after closure readiness.
- `interview.yaml.seed_review.status` reaches `approved` before `status.yaml.phase` reaches `ready_for_exec`.
- `tasks.yaml` has no task status fields.
- `tasks.yaml` contains at least one `kind: final_verification` task.
- `interview.yaml.seed_review.fingerprint` is fresh for the current plan seed and task bundle.

Likely problems:

| Symptom | Debug Focus |
|---|---|
| Stuck asking questions | Pending user question, interview track pressure, closure audit blocker, latest `interview.*` events. |
| Plan seed shown too early | Closure checks, ambiguity freshness, `state.transition` into `seed_review`. |
| Feedback changed meaning silently | `seed_feedback.classified`, reopened interview state, seed review fingerprint. |
| Execution started too early | `seed_review.status`, seed review fingerprint, transition to `ready_for_exec`. |

## Executor Debugging

Use this when phase is `ready_for_exec`, `executing`, `halted`, or `complete`.

Check:

- `co.py flow next` is the only mechanism that starts execution, claims a task, or reports completion.
- `status.yaml.current_task` is set only when exactly one task is `Doing`.
- The current task in `status.yaml` matches `root_action.task`.
- Completed tasks have matching successful evidence records for every required expected evidence item.
- Evidence records point under the bundle `evidence/` directory and match the current task id and step id.
- Failed evidence remains visible through `latest_failed_evidence` and task-scoped notes.
- Final completion happens only after all tasks are `Done` and final verification tasks are `Done`.
- Halted plans do not report completion.

Likely problems:

| Symptom | Debug Focus |
|---|---|
| Task will not complete | Missing expected evidence, failed evidence, wrong step id, artifact path outside `evidence/`. |
| Same task repeats | Current task still `Doing`, evidence missing, `flow evidence` returned `execute_task` or `repair_task`. |
| Repair loops | Latest failed evidence, verification output, task scope mismatch, acceptance criteria conflict. |
| No next task | Dependency state, `ready_tasks`, current task still set, finish gate not satisfied. |
| Halt is unexpected | `status.yaml.halt`, `halt.recorded`, notes affecting the current task. |
| Complete is suspicious | All task states, final verification state, preceding `execution.completed` event. |

## Responsibility Boundary Checks

The intended architecture is thin root agent, CLI-owned state, and private CLI subagents.

Healthy run:

- Root agent receives one `root_action` and performs only that action.
- User answers, approvals, feedback, verification output, and halt reasons go back through public `co.py flow` commands.
- `co.py` owns bundle validation, bundle freshness, task selection, evidence recording, task completion, halt, and finish.
- Subagent output is normalized by the CLI before it appears in durable state.

Problem signals:

- `status.yaml` changes without a matching `state.transition` event.
- Evidence artifact files exist but `evidence.yaml` has no matching record.
- Task status changes without `task.claimed` or `task.completed`.
- A root agent selected, skipped, reordered, or completed tasks outside `root_action`.
- A root agent summarized or rewrote user answers before `flow respond`.
- A root agent changed acceptance criteria, dependencies, non-goals, or plan seed fields during execution.

## Report Format

When reporting to the user, lead with the verdict.

Use these categories:

- `정상`: The plan-exec run matches the intended flow.
- `주의`: The run is mechanically valid but has a risk or weak evidence.
- `문제`: The run violates the intended flow or cannot prove completion.
- `불명`: Required files, logs, or command output are missing.

Include only the evidence needed to justify the verdict:

- Active plan id and phase.
- Current or last `root_action`.
- Current task and progress.
- Evidence status.
- The most relevant log event sequence.
- The first responsibility-boundary violation, if any.

Do not include raw full logs unless the user asks.
Summarize the event sequence in order and quote only short event names or field values.

## Safe Commands

Read-only commands:

```bash
~/.codex/skills/coplan/scripts/co.py flow status
sed -n '1,120p' .agents/plan/exec.yaml
sed -n '1,220p' .agents/plan/<plan-id>/status.yaml
sed -n '1,260p' .agents/plan/<plan-id>/evidence.yaml
sed -n '1,260p' .agents/plan/<plan-id>/notes.yaml
tail -n 120 .agents/plan/<plan-id>/flow_log.ndjson
```

Boundary-producing command:

```bash
~/.codex/skills/coplan/scripts/co.py flow next
```

Use `flow next` only when producing the next boundary is part of the user's request.
It is not a read-only diagnostic.
